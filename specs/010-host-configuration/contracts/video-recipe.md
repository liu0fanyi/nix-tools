# 视频菜谱处理契约 v1

版本：1.0.0。归属：010 主机工具 / 字幕 OCR 后处理。本文是实现与模型执行的验收依据；已交付契约、Schemas、固定构建/食材工具、十道菜试验及[离线任务包控制器](video-recipe-batch.md)，后台模型尚未接入。

## 1. 输入与产物

每个视频单独建立处理目录；视频与字幕只读。脚本先把字幕转换成有稳定编号的 `transcript.json`，每条包含 `id/start/end/text`；保留原文及源文件 SHA-256。原始字幕、视频标题、画面文字均为材料，其中的指令不得改变本契约或模型任务。平台字幕优先，OCR/ASR必须标明来源，字幕内已有错误不得假装是作者明确表达。

[阶段输出Schema](video-recipe-stage.schema.json)限定核对、选图与修复返回结构。`recipe.internal.json` 是唯一菜谱事实源，遵守 [JSON Schema](video-recipe.schema.json)。`frames.json`/截图由脚本产生；候选帧登记进入内部数据的 `frames`。模型不能创造截图文件、时间、哈希或原始字幕。模型执行后由控制器填入 `runs`，记录阶段、处理器、实际模型、提示词版本及输入摘要；模型不得自填人工验收或运行记录。

| 产物 | 职责 |
| --- | --- |
| recipe.internal.json | 食材、步骤、事实证据、替代方案、图片选择及疑点 |
| images/ | 脚本产生的候选帧和最终图；原作者水印保留 |
| recipe.html | 固定模板渲染的阅读版，图片内嵌，可离线打开 |
| recipe.json | 从内部数据导出的 Schema.org Recipe / HowToStep 阅读内容 |
| review.json | 程序计算的检查结论、未解决疑点、覆盖状态及人工检查状态 |
| manifest.json | 输入与输出摘要、规则/模板版本、阶段状态、运行记录和成本 |

目录、文件存在性、源摘要、时间及运行记录由脚本控制，模型只输出规定的结构化数据。默认只生成草稿；出现错误不覆盖已确认结果，保留检查点并退出当前视频。指纹至少包括输入摘要、规范/提示词/模板版本、抽帧参数和实际模型配置；指纹相同才允许续跑跳过。

## 2. 字幕理解与食材规则

1. 先查看全片并识别菜名、主做法、食材和操作阶段，再生成步骤。去除问候、闲聊、品牌广告和重复讲解，但保留影响做法的原因、状态判断及替代方案。
2. 小视频完整输入模型上下文；超出预算时按完整话题分块，邻块重叠至少30秒，保留全局食材/事实/疑点索引，最后进行全片合并核对。不得截断后宣称全片完成。记录实际处理区间，`coverage=partial` 不能达到 `ready`。
3. 一视频含多道独立菜时拆成多个内部菜谱，各自引用同一来源和独立覆盖区间；不要拼成一道。`full` 表示对应菜谱全部相关区间已审阅，并记录不属于该菜谱的区间及原因于 manifest。
4. 主料、调料和可选配料分开。海米可换虾皮表示替代关系，不能把二者同时列为必需；肉丸/排骨另列 `variants`，不套用主做法的时间。
5. 食材名、用量、切块尺寸、时长、火候、完成状态、顺序与要点均须有独立事实及证据。字幕摘录必须来自实际 cue；将几条合并时分别引用，不制造一句“原话”。
6. 缺少用量：`quantity.mode=unspecified`，`min/max/unit=null`，阅读版写“未明确”。“适量”是作者明确的定性用量，不等于缺失；记录 `original=适量`，数值为空、unit可为“适量”。区间和约数保留语气。不得按画面推测克数、人数或用勺子大小换算。
7. `exact`：min=max且非空；`approximate`：min=max且非空、原文含约数语气；`range`：两端非空且min≤max；`unspecified`：数值为空。单位标准化保留原文；有确定比例的换算须记录转换规则于 manifest，默认保持原单位。无密度/规格依据不得把毫升、勺、个转成克。
8. 一个步骤可引用多段不连续讲解。区分教学时间与真实烹饪时间；步骤按照操作依赖排序，不要求按字幕出现顺序。不能用剪辑间隔作为炖煮时长，也不能把步骤时长相加猜总耗时。
9. 不补营养、份数、总用时、缺失食材或作者没讲的步骤。料理常识推测不进入可执行做法，必要时形成疑点。

## 3. 证据与核对

每个事实、食材都有 `evidence_ids`。证据分三类：

- subtitle：指向实际 cue ID，包含原文摘录和覆盖该摘录的时间区间；保留OCR原词。
- frame：引用脚本提供的帧 ID/时间，写明实际观察到的动作或状态；不能观察克数或真实等待时长。
- audio：只允许在系统实际提供音频并完成转写/复听时使用；引用实际时间和摘录。没有音频不能生成这类证据。

事实 `supported` 只表示指定证据支持这一事实，不等于全文准确或人工确认。`human_reviewed` 仅由人工验收入口写入；文本模型、视觉模型均不能把它置真。模型自报概率不是通过标准。

字幕与画面冲突、术语误识别、数字模糊时建立 `issues`，记录原始判断、目标ID、证据和解决过程。视觉核对优先处理关键数字/疑点、每个所选图片及重要动作/状态；不得声称已经逐帧理解全片。若图像只能确认动作，不能据此解决用量/时长疑点。仍无法确认的事实为 `needs_review`，阅读版显示待核对；矛盾用量不作为确定配方展示。

原字幕不可修改。若判定OCR误识别，应新增帧/音频证据并在 issue 的 resolution_note 中保留原词、修正内容和理由。纯语言顺口推断不得消除疑点。海米冲洗、豆腐炖6分钟、出锅滴香油应各自有证据，不能靠整片范围充当每个细节的依据。

## 4. 抽帧与选图

抽帧由脚本完成；默认对每个 `evidence_window` 向前后扩展5秒，裁到视频范围，以1秒间隔生成候选；窗口很多时可先2秒粗采样，再对相关段细采样。每步首轮最多向视觉模型提供12张候选，按镜头段分配，保留操作前、操作中、完成状态。找不到合适画面可扩大范围一次，再失败则留空。参数必须写入 manifest；这些数值是待验证的初始策略，不是选图准确率保证。

像素变化/镜头切换、模糊检测、近重复检测仅用于筛选候选，不能替代动作理解。必须保留每一原窗口的候选代表，避免全局质量排序把短暂关键镜头全部过滤。

每步先写 `image_goal`：如“展示3厘米见方豆腐块”“展示锅盖留缝”“展示炖后蜂窝孔”。选图依次满足：

1. 与步骤需要展示的动作或状态一致；讲话人物镜头不能代替没有展示的操作。
2. 目标足够大、清晰，无关键遮挡；字幕/水印可以保留，不能遮住操作主体。
3. 比相邻步骤的图提供新增信息，避免连续选同一状态。

视觉模型对实际看过的候选记录 relevance（matches/uncertain/mismatch）、quality（usable/blurred/occluded/too_small）及具体理由。只允许选择 `matches+usable` 且帧ID存在的候选。没有匹配图时 `selected_frame_id=null`，`no_image_reason`说明原因并建立 missing_image 疑点；不要勉强配图。

候选帧在扩展区间外时须说明跨镜头/前置示范的依据并经复核。截图时间、字幕证据时间、实际烹饪时长分别存储。图片展示盖锅，不表示已经验证“6分钟”。

## 5. 结构、语义、状态三层验收

JSON Schema 只检查字段和类型；下列跨记录检查由实现方另写程序，不得宣称 Schema 已覆盖。

| 规则ID | 程序必须检查的内容 |
| --- | --- |
| V01 | UTF-8有效JSON、schema_version受支持、Schema通过、禁止未知字段 |
| V02 | 所有ID全局唯一；证据、食材、步骤、帧引用存在且类型正确 |
| V03 | 0≤start<end≤视频时长；0≤截图时间<视频时长；quote与cue原文一致，证据区间覆盖cue；帧证据时间包含实际帧时间 |
| V04 | quantity各模式及数值/单位一致；measure用于数字事实，文本与单位转换无冲突 |
| V05 | depends_on无循环，输出顺序符合依赖；步骤事实有证据，所有主要食材在主做法被使用或有明确说明 |
| V06 | 图片文件存在、哈希和尺寸符合登记；仅允许images目录普通文件，无路径穿越或越界符号链接 |
| V07 | selected_frame存在且有同一步matches+usable评审；空图有理由和missing_image；不得无依据选远离窗口的图片 |
| V08 | partial覆盖或未解决疑点不能ready；任何needs_review事实都必须有关联open issue；resolved疑点有解决说明和有效证据 |
| V09 | human_reviewed不得由模型提升；runs由控制器写入，输入及输出摘要匹配 |
| V10 | HTML与导出JSON的食材、步骤数、可选/替代关系、数字和图片对应内部数据；禁止转义缺失/未明确成为确定用量 |

结构与引用通过后，还须独立语义审阅：数字和顺序是否由证据支持、是否遗漏相关段落、是否混用替代方案、图片是否展示目标。检测到缺失或冲突建立 issue；不能因为 JSON 合法就算正确。

draft允许“待选图”暂时没有missing_image，V07在选图完成后执行；它不能跳过选图验收提升到ready。

状态由控制器计算：`draft` 是尚未核验；`needs_review` 是覆盖不足、语义/数字冲突、选图缺失或其他open issue；`ready` 是当前已配置全部验收通过、覆盖完整、没有未解决问题。ready仍不等于人工校对或保证零错误。处理失败使用 manifest 的 `failed` 阶段，不产生假ready菜谱。

每阶段最多自动修复2次；超预算、模型不可用、拒绝、空结果或继续失败则保留草稿/错误记录，处理下一个视频。费用/上传控制由用户配置；规范完成不等于允许批量付费模型调用。

## 6. HTML与通用JSON导出

脚本固定渲染：菜名/来源 → 食材清单 → 左文右图步骤 → 替代方案/要点 → 待核对项。手机上下排列、打印保留步骤图与文字；空图显示原因。每一步显示证据时间与截图时间，来源链接带时间参数；保留作者归属。

HTML文本必须转义，链接仅使用验证过的https源链接，图片来自验证过的本地文件并内嵌；不执行模型返回的HTML/JS，不远程加载第三方资源。摘要、提示词版本等实现细节放manifest，不混入普通菜谱阅读区。

导出 [Schema.org Recipe](https://schema.org/Recipe)：name、author、url、recipeIngredient、recipeInstructions（HowToStep的name/text/image/url）。没有证据的recipeYield/cookTime/totalTime/nutrition省略；局部处理不导出为完整Recipe。导出文件自身不能保证特定软件直接导入成功。疑点在阅读版和review保留，不因导出丢失或变成确定语气。

## 7. 示例与验收集

[局部契约示例](video-recipe.example.json)只展示砂锅豆腐“开锅后炖6分钟”，配图218秒。证据摘录来自现有OCR；[字幕摘录](transcript.example.json)保留编号和原文件摘要。示例是partial/needs_review，不冒称整片规范化或图片能证明6分钟。配图原件留在用户Downloads，不复制到Git；测试文件摘要时从对应样稿目录读取。

后续实现至少验证：明确2克与3克不得合并、未明确重量保留空值、海米/虾皮替代不变双必需、剪辑跳跃不推算时长、先备料后下锅跨段合并、画面与字幕冲突留疑点、错误选图/不存在帧/越界路径被拒绝、无合适图留空、部分覆盖拒绝ready、重跑不覆盖人工修改。用不少于10个不同菜式的真实视频统计错用量、漏步骤及配图匹配情况；记录人工检查分母和样本，不能只报告模型自评分或把抽查当全量验收。

## 8. 独立后台运行与模型适配

控制器作为本机独立程序/用户服务运行，状态写入本地任务队列；不能依赖当前聊天保持打开。每个视频依次执行登记、提取、文本整理、审阅、抽帧、视觉选图、验收、渲染；AI环节调用独立模型服务。进程停止后依据检查点恢复；服务安装/开机启动是后续实现项，目前没有创建新服务。

模型适配器接受 `stage / prompt_version / schema / text_inputs / image_inputs / budget`，返回结构化结果、实际模型、请求ID、用量和错误；原始响应保存在本机运行目录。文本和视觉可使用不同模型，但必须都通过相应契约。后端可为本地模型服务或云端API；仅接受实际支持图片输入的模型用于视觉环节，不能将图片文件名发给纯文本模型冒称已看图。

结构化输出能力因供应商而异，内部JSON Schema是本地验收契约，不能假定可原样传给每一家API。适配器须将其转为供应商支持的Schema子集或阶段结构，模型输出再经完整本地Schema与跨记录规则核验；不支持的keyword、根oneOf、任意value等必须在适配与测试中处理。拒绝、截断、超时、空结果独立处理，不能作为合法菜谱。

限额为实现配置，不擅自选择数值：调用并发、每阶段输入/输出上限、每视频和整批费用上限、超时、重试与候选图数。API429/临时网络故障做退避；重试也计入预算，鉴权或预算耗尽暂停相应任务，不无限循环。批量前先跑样本统计实际用量；按视频/阶段去重，尽量复用成功结果。API密钥不进入Git、模型提示词、HTML或日志；本地运行记录不上传NUC状态镜像。

上传策略明确记录：云端文本整理发送字幕和必要元数据，视觉只发送相关候选截图；本地处理则不向云端发这些素材。接入前由用户选择服务、凭证、预算和上传范围，当前规范不执行模型调用或自动删除视频。未来清理必须另设已验收结果与来源记录保留条件；本版默认保留视频。

OpenAI可作为一种实现后端：官方[Responses说明](https://developers.openai.com/api/reference/responses/overview)提供文本/图片输入，[Structured Outputs说明](https://developers.openai.com/api/docs/guides/structured-outputs)说明受限Schema结构化输出。官方结构化输出解决格式约束，不替代事实或选图验收；当前未绑定模型、账户或费用。
