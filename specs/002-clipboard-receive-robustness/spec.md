# 特性规格：clipboard-sync 接收体验与错误健壮性

**Feature Branch**: `002-clipboard-receive-robustness`

**Created**: 2026-09-10

**Status**: Draft

**Input**: User description: "把 clipboard-sync/todo.md 中真实剩余的需求转成 spec；已完成的条目为既成事实，待决策项列为 Open Questions。"

## 背景与目标 (Context & Objectives)

`clipboard-sync` 的三端（Linux/Windows/Android）基础传输链路已实现并验证：内容类型（文字/图片/文件）、大文件流式传输、防广播回环、三端通知与确认交互均已落地。

本规格只覆盖**尚未完成或体验待改善**的部分，来源为 `clipboard-sync/todo.md` 与 `docs/clipboard-sync-refactor.md` 的遗留项：

1. **错误提示不友好**：传输超时仍向用户直接显示 `Try again (os error 11)` 这类系统错误码。
2. **图片不能写入系统剪贴板**：接收图片时只保存文件，未写回剪贴板（传输为原始 RGBA 无尺寸信息）。
3. **若干接收行为原未定义**：确认超时策略、多设备同时复制、历史记录需求（均已在本规格 resolve，见 Clarifications）。
4. **参考副本状态未确认**：`refs/` submodule 状态。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 失败时看到可理解的原因 (Priority: P1)

传输失败时，用户看到的是一句能理解、能据此行动的中文提示，而不是 `os error 11` 之类的系统错误码。

**Why this priority**: 直接决定用户能否自行恢复；当前是已知最刺眼的体验缺陷。

**Independent Test**: 制造发送方离线、连接被拒绝、传输中断三种失败，确认每次显示的都是可理解提示且保留原始错误供排查。

**Acceptance Scenarios**:

1. **Given** 接收方等待数据但发送方已离线，**When** 超时触发，**Then** 用户看到"接收超时，请确认发送方在线且两端网络正常，再点击重试"类提示，而不是 `os error 11`。
2. **Given** 目标端口无服务监听，**When** 连接被拒绝，**Then** 提示与"超时"可区分，指向连接问题。
3. **Given** 传输中途连接中断，**When** 读取失败，**Then** 提示说明传输中断，且本地文件 I/O 错误仍保留其原有信息（不被误映射）。

---

### User Story 2 - 接收的图片直接可粘贴 (Priority: P2)

用户接收一张图片后，可直接在目标应用里粘贴，无需先去下载目录找文件。

**Why this priority**: 补齐"接收即入剪贴板"的既有承诺——目前文字已支持，图片只有落盘。

**Independent Test**: 从一台设备复制图片，在另一台设备接收后立即粘贴到绘图/聊天应用，确认图片内容出现。

**Acceptance Scenarios**:

1. **Given** 接收方收到图片内容，**When** 用户点"接收"，**Then** 图片既写入默认文件夹（PNG），也写入系统剪贴板。
2. **Given** 图片已写入剪贴板，**When** watcher 检测到剪贴板变化，**Then** 防回环机制生效，不重复广播。
3. **Given** 接收端运行在没有剪贴板图片支持的平台，**When** 接收图片，**Then** 至少完成文件保存，并明确告知剪贴板写入不可用（不静默失败）。

---

### User Story 3 - 待接收提示的行为可预期 (Priority: P3)

当多个内容接连到达，或用户长时间不响应时，待接收提示不会堆积、错乱或无限期悬挂。

**Why this priority**: 影响使用体验但不阻断主流程；当前已有"只显示最新一个"的改进。

**Independent Test**: 连续发送多条内容、以及发出后不响应，观察提示数量与超时行为。

**Acceptance Scenarios**:

1. **Given** 已有一个待接收提示未处理，**When** 新内容到达，**Then** 新内容胜出，被顶掉的项显示"已被更新内容取代"，不出现堆积。
2. **Given** 提示长时间无人响应，**When** 超过 2 分钟，**Then** 该待接收项自动失效并显示"已过期"，用户无法再对其执行接收操作。
3. **Given** 两台设备几乎同时发来不同内容，**When** 两项都到达，**Then** 后到达者成为唯一待接收项，先到达者显示已被取代。

---

### Edge Cases

- 发送方与接收方**同时**复制不同内容（多设备冲突）。
- 传输过程中接收方磁盘写满或目录不可写。
- 剪贴板中已有内容被用户手动修改，与待接收内容交错。
- 同一内容在短时间内被重复广播（已被 30 秒去重窗口覆盖，需确认图片场景同样生效）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 传输超时 MUST 向用户显示可理解的中文说明，并给出可执行的下一步建议。
- **FR-002**: 连接被拒绝 MUST 与超时区分显示，不得共用同一条提示。
- **FR-003**: 错误映射 MUST 保留原始错误信息（source），供日志排查；MUST NOT 丢弃或覆盖。
- **FR-004**: 本地文件读写错误 MUST NOT 被映射为网络类提示。
- **FR-005**: 接收图片时 MUST 同时完成"保存文件"与"写入系统剪贴板"两项动作（平台支持时）。
- **FR-006**: 图片写入剪贴板 MUST 复用既有防回环机制，不产生重复广播。
- **FR-007**: 平台不支持图片剪贴板时 MUST 明确告知用户，MUST NOT 静默失败。
- **FR-008**: 待接收提示的并发与超时行为 MUST 有明确定义并实现一致（Linux/Windows 行为对齐）。
- **FR-009**: 错误映射与提示逻辑在三端（Linux/Windows/Android）共享，MUST NOT 各端重复实现。
- **FR-010**: 现有成功路径行为 MUST NOT 回退：文字/图片/文件/目录 ZIP 的接收流程保持不变。
- **FR-011**: 待接收项 MUST 在发出后 2 分钟自动失效，失效后 MUST 向用户显示"已过期"且拒绝后续接收操作。
- **FR-012**: 超时时长 MUST 为固定值 2 分钟，本规格阶段 MUST NOT 引入用户可配置项（保持实现与测试简单）。
- **FR-013**: 多项待接收内容并发到达时 MUST 采用"最新到达者胜出"策略；被取代的项 MUST 提示"已被更新内容取代"，MUST NOT 静默丢弃。

### Key Entities

- **错误类别**：超时、连接被拒绝、传输中断、本地 I/O 失败——决定提示文案。
- **用户可见提示**：面向用户的文案（中文），与原始错误分离。
- **剪贴板写入能力**：平台是否支持图片写入系统剪贴板。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 三种失败场景（超时/拒绝/中断）各自显示不同且可理解的中文提示，0 处直接暴露系统错误码。
- **SC-002**: 接收图片后可直接在外部应用粘贴成功，验证 ≥2 个应用。
- **SC-003**: 图片接收不触发重复广播（`[skip]` 防回环日志可见）。
- **SC-004**: 既有回归测试全部通过，且新增失败场景测试覆盖上述三种错误映射。
- **SC-005**: 三端错误映射共用同一实现，代码中不存在重复的错误文案分支。

## Assumptions

- **基础链路已可用**：三端传输、通知、确认交互、防回环均已实现并验证（见 todo.md 已完成条目），本规格不重新设计这些部分。
- **失败场景可通过受控方式复现**：超时/拒绝/中断可用测试或手工构造验证。
- **图片进剪贴板受平台限制**：部分平台可能不支持，规格允许"明确告知"作为降级。
- **代码归属**：实现位于 `clipboard-sync` 子模块；规格文档由 nix-tools 管理（本项目约定）。
- **参考副本按需检出**：`refs/` 下的上游参考副本子模块（arboard/muda/notify-rust/tray-icon/windows-rs）保留声明但不纳入默认检出；需要 diff 对照时按需执行 `git submodule update --init refs/<name>`。
- **图片传输格式不变**：维持协议现有的"宽高 BE + 原始 RGBA"格式；接收端复用已有 `save_rgba_payload_png` 编码 PNG 写入剪贴板。本规格不引入压缩或协议变更。
- **范围边界**：不含 Android 端新功能、不含传输协议变更、不含 UI 重设计、**不含已接收历史记录功能**（如需另开 spec）。
